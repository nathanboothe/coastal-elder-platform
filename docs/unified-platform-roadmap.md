## 3. Target architecture: one backend

**Shape of the change:** retire `elder-android-backend` and `coastal-elder-scheduler`'s `server/` as two independent services, and stand up one Express API — call it `elder-api` for now — that both the web client and the mobile app call. It owns one copy of every route currently duplicated or diverged between the two: WAC code validation, campus/date/time/elder availability, appointment booking, the M365 group Refresh sync, and Graph email sending.

**Auth model — corrected Aug 27 after reading the actual source (the repos were made public for this session):** this section originally proposed consolidating web and mobile onto one shared Entra app registration. That was wrong, and not just as a guess — the web app **already has** real Entra SSO for `/manage`, built and deployed, and it deliberately uses its **own separate** confidential-client registration rather than sharing mobile's. The code's own comments explain why, and it's correct OAuth practice, not an oversight to fix: mobile is a **public client** (Authorization Code + PKCE, no secret) and web is a **confidential client** (Authorization Code, holds a real client secret server-side) — mixing a public and confidential client under one registration is the anti-pattern, not the improvement. Keep them separate. What *is* shared, correctly, is the two underlying Entra **security groups** (`ENTRA_GROUP_ID_ELDERS`, `ENTRA_GROUP_ID_ADMINS`) — group membership is a tenant-level concept, so both app registrations check the same groups for role, without needing to share a client ID or secret to do it.

Practically, this means the "port Entra SSO to web" work this section originally scoped for Phase 3 is **already done** — `server/lib/manageAuth.js` and `entraAuth.js` implement the full login flow, JWKS-based token verification, and role assignment. Phase 3's actual remaining work is narrower than planned: retire the *old* PIN-based code paths if any still linger, and reconcile the WAC/session model between web (`SCHEDULER_SESSION_SECRET`) and mobile (still shows `SCHEDULER_PIN` + `JWT_SECRET` in `elder-android-backend/config.js` as of Aug 27 — worth confirming whether that's live or vestigial before assuming mobile needs the same change web already made).

**Database: confirmed — staying on Airtable.** No migration to Postgres as part of this initiative. The reasoning: the clone-and-configure model means each church deployment gets its *own* Airtable base, so the 1,000-record cap that worried the source docs becomes a per-church ceiling, not a ceiling on your only customer. Coastal itself (32 elders, their availability rows, appointments, WAC codes, all sharing one base's 1,000-record pool) is still worth watching as it grows, so the unified API's data-access layer should still sit behind a repository/interface abstraction — a thin module other code calls instead of hitting the Airtable SDK directly — so that if Coastal (or a future church) ever does hit the cap, swapping in Postgres for just that deployment doesn't mean rewriting the routes, only the data layer underneath them.

**Entra tenant sequencing:** build and test everything against TechFoundry360's existing tenant now — that's already where today's app registrations live, so this continues current practice rather than changing it. The one Entra app registration this plan consolidates web and mobile onto (Section 3, above) gets created in that tenant first. When Coastal grants access to their own tenant, the swap is: register the same app there, update `ENTRA_TENANT_ID` / `ENTRA_CLIENT_ID` / the two security-group IDs in Render's env vars, and re-point the mobile app's equivalent config for its next build. Because those are already env vars rather than hardcoded values (per the source docs' existing convention), this is the tenant-migration item from the web app's known-gaps list — now scheduled deliberately rather than indefinitely deferred.

**What this does to the two known-blocked features:** the elder Outlook calendar sync (blocked on ~30 of 32 elder records missing M365 Object IDs) and mobile's confirmation email both touch the same identity/directory code this unification rewrites anyway. Section 6 sequences them in rather than treating them as separate later work.

## 4. Repo and codebase consolidation

Render already handles a monorepo-with-subdirectories pattern for MAP (`Root Directory: server` for the API service, a separate static site service for the client) — the same pattern applies here and keeps each service's build isolated even though the code lives together.

Proposed layout, consolidating what's currently three repos (`coastal-elder-scheduler`, `elder-android-app`, `elder-android-backend`) into one:

```
coastal-elder-platform/
  server/          ← unified elder-api (replaces server/ and elder-android-backend)
  client-web/      ← React + Vite (was coastal-elder-scheduler's client/)
  client-mobile/   ← Expo/React Native (was elder-android-app)
  shared/          ← types and constants both clients need (campus list, date/time formatting helpers — the UTC-bug pattern both docs flag separately should live in exactly one place)
render.yaml
```

**Correction, Aug 27:** the original web app is actually a **single** Render service that serves both the API and the built static client itself — `server/server.js` builds nothing on its own but serves `client/dist` via `express.static`, with the buildCommand building the client first. It's not the two-service split (Web Service + Static Site) MAP uses, and this document previously assumed a split without confirming that. Worth a deliberate choice rather than defaulting to MAP's pattern: keep the one-service-serves-both approach (simpler, matches what's already proven in production, but means the API and the client always deploy together), or split it now while already restructuring. Either way, one concrete bug either path needs fixed first: `server.js`'s static-serving path is hardcoded to a sibling folder literally named `client` (`path.join(__dirname, '..', 'client', 'dist')`), which breaks silently (no crash, just serves nothing) under this repo's `client-web` naming — a one-line path fix once the direction is chosen.

If a split is chosen: two Render services point at this one repo, a Web Service rooted at `server/`, and a Static Site rooted at `client-web/`. The mobile client isn't a Render service at all — it ships through EAS, covered next — but living in the same repo means a backend API change and the mobile code that depends on it move together in one commit instead of two repos drifting out of sync, which is exactly the kind of gap that caused the original 401 that split the backends apart in the first place.

**Confirmed: this repo is private, and you execute the consolidation yourself.** Unlike `coastal-elder-scheduler` today (public), the new `coastal-elder-platform` repo gets created as private from the start — one less thing to worry about once elder/appointment data or Entra config lives anywhere near it, even in env-var references. The step-by-step for doing this in GitHub Desktop, without local Node, is written up separately in the companion **Repo Consolidation Runbook** rather than repeated here — it covers creating the private repo, the exact folder-copy sequence from the three existing repos, and the Render private-repo access step that trips people up (Render's GitHub App needs to be explicitly granted access to a new private repo — it isn't automatic).

## 5. Dev pipeline: nothing reaches production without you

The goal you stated is specific: dev work should never reach production without a deliberate act on your part. Render's own documented pattern for this is branch-to-service binding — each Render service tracks exactly one branch, and there's no automatic path from one service to another except through Git itself. Concretely:

| Branch | Render service | Purpose |
|---|---|---|
| `dev` | `elder-api-staging`, `elder-client-staging` | Every push here deploys immediately. This is where iteration happens — yours or mine. |
| `main` | `elder-api` (production), `elder-client` (production) | Only deploys on merge to `main`. |

**Reality check, Aug 27 (see Section 9 below for the full story):** this table describes the *intent*. What's actually running as of Aug 27 is inverted from it — the service actually serving real custom-domain traffic tracks `dev`, and the service named like production (tracking `main`) is stale and unbuilt. Section 9 has the details and what it means going forward; don't assume this table reflects current reality without checking Section 9 first. **Update, Sep 3: resolved** — see Section 9, "`main` promotion executed" — both services are at parity as of Aug 27 evening; only the cosmetic label/URL mismatch remains open (tracked as a Todoist backlog item).

The deliberate action is the promotion step: a pull request from `dev` into `main`. With a branch-protection rule on `main` requiring that PR (even a self-reviewed one, opened and merged through GitHub Desktop or GitHub's web UI rather than a direct push), production simply cannot change except through that explicit step — which is exactly "never reaches production without me doing it." This fits your existing GitHub Desktop workflow; the only new habit is merging through a PR instead of pushing straight to `main`, which GitHub Desktop supports natively.

Each environment needs its own env vars and, practically, its own Airtable base (or at minimum a clearly separated set of tables) so staging test bookings never touch Coastal's real data — Render's "environment groups" feature (shared config scoped to one environment, invisible to the other) is built for exactly this and is worth using instead of duplicating var lists by hand.

**Mobile is a separate release train and needs its own version of the same idea.** EAS already has the pieces: build profiles in `eas.json` (`development`, `preview`, `production`) that can each carry a different `API_URL` pointing at staging vs. production `elder-api`, and EAS Update channels that let you push JS-only updates to a `staging` channel for testing before republishing the identical bundle to `production` — so testers on a preview build see changes before anyone using the store build does, without a new store submission for every change. Native-code changes still need new builds per profile; JS-only changes can go through channels. Given iOS hasn't had a first build yet, this is also the natural point to set up its profile and bundle identifier rather than bolting it on afterward. **Update, Sep 3:** the iOS bundle identifier (`org.gocoastal.elderscheduling`) was set back on Aug 29/Sep 1, ahead of this note. See Section 11.

One thing this pipeline doesn't cover on its own: automated checks before a merge is even allowed. A lightweight GitHub Actions workflow that runs a build/lint check on every PR into `main`, wired into the branch protection rule as a required status check, would catch broken builds before they're even eligible to merge — optional, but cheap to add given you already have GitHub Actions available for free on a public repo, and it keeps the "deliberate action" from being just a rubber-stamp click.

## 6. White-label: clone-and-configure per church

The chosen model means Coastal's deployment becomes the reference implementation of a template, not a special case. The concrete work is finding every place "Coastal" is currently load-bearing in the code and making it configuration instead.

| Currently hardcoded | Becomes |
|---|---|
| Campus list (Battery Park, Bethany, Chesapeake, Gloucester, Hampton, Mathews, Williamsburg, Yorktown) | A config file or table the new church populates — nothing in code should assume 8 campuses or these names |
| `gocoastal.org` domain references, `scheduling@gocoastal.org`, `engagement@gocoastal.org` | Env vars per deployment |
| Coastal logo (`client/public/logo.png`), brand colors | A `branding/` folder each deployment swaps, referenced by config rather than a fixed filename |
| Airtable base ID, Entra tenant/client/group IDs | Already env vars per the source docs' convention (`sync: false` in `render.yaml`) — just needs to be a documented, complete list, not partially in code |
| "WAC" / "We Are Coastal" terminology, 7-day lead time rule | Config-driven labels and a configurable lead-time value, since another church's membership class and timing rules won't match Coastal's exactly |
| Airtable table *names* hardcoded as string literals in `server/config.js` | Worth reconsidering — `elder-android-backend`'s config parameterized table names via env vars instead, which is actually a better starting point for this phase than what got kept during the Phase 3 backend merge. Not changed as part of Phase 3 (out of scope for that pass), but worth doing here rather than re-deciding it later. |

The deliverable for this phase isn't just code changes — it's a **New Church Setup Runbook**, the same genre of document as the existing Migration Runbook, but written for "stand up a new church" instead of "move Coastal to its own tenant." It should cover: fork the repo, create a new Airtable base (Airtable's base-duplication feature can seed it from a template base with the schema already in place), register a new Entra app (a **new tenant** this time — this makes the currently-deferred "Entra tenant migration" item from the web app's known-gaps list a hard requirement for the white-label path, not just Coastal's own cleanup, since another church obviously can't run through TechFoundry360's tenant), set the env var list, and deploy the Render services from `render.yaml`.

Worth being explicit about the tradeoff you picked: clone-and-configure means every new church is a genuinely separate deployment you stand up and that keeps you as the maintainer of N codebases-in-sync rather than one multi-tenant system — lower ops burden per instance, but the runbook and the discipline of actually keeping deployments in sync when you fix a bug is what makes it scale instead of drifting into N slightly-different forks over time.

## 10. Phase 4 kickoff — the M365 Object ID backfill problem (Aug 27)

Nathan chose to tackle Phase 4 next: the M365 Object ID gap, the elder Outlook calendar sync it blocks, and mobile's confirmation email. Before writing any code, read the actual sync implementation (`server/lib/elderSync.js`, `server/lib/graphDirectory.js`) to check the source docs' "likely resolution: backfill via a Refresh-from-M365 run" note against what the code actually does.

**It doesn't work as hoped — worth flagging before anyone clicks that button.** `refreshFromM365()` matches M365 group members to existing Elder records **only by M365 Object ID**, and it explicitly, permanently excludes every `Source = 'Manual'` record from being touched at all — `getPreviouslySyncedElders()` only reads records where `Source = 'M365 Group Sync'`; the code's own comment says manual elders (the Demo record and the original 30-person roster) are out of scope for this sync by design.

That means the ~30 manually-seeded elders currently missing an Object ID can't be matched by this sync — they have no Object ID to match on, and their `Source` field excludes them from the lookup entirely. If "Refresh from M365" gets clicked as-is, for every one of those 30 people still in one of the three elder groups, the sync will see "no existing record with this Object ID" and create a **brand-new, duplicate** Elder record (`Source = 'M365 Group Sync'`) — leaving the original Manual record untouched, orphaned, and now duplicated. Since Availability, WACCodes, and Appointments all tie to an elder by *name* rather than a stable ID, a duplicate record for the same person is a real data-integrity problem, not cosmetic clutter.

**What actually needs to be built instead:** a one-time backfill step that matches each existing `Source = 'Manual'` Elder record to its corresponding M365 user (most likely by email — Airtable's `Email` field vs. Graph's `mail`/`userPrincipalName`, the same fallback `graphDirectory.js` already uses for the group sync) and writes the `M365 Object ID` onto the **existing** record, without touching `Source`. Only after that backfill runs should "Refresh from M365" ever be clicked normally — otherwise it'll immediately start creating duplicates for anyone the backfill missed.

This corrects the "likely resolution" note carried over from the source docs into Sections 1, 3, and 9 above — the fix needs new code, not just an existing button. Decided with Nathan: exact email match (not case/whitespace-normalized — a near-miss is reported separately for manual review, never auto-applied), and a dry-run-first design (nothing writes to Airtable unless a second call explicitly confirms).

**Built, tested, and delivered.** New `server/lib/elderObjectIdBackfill.js` plus `POST /api/elder-sync/backfill-object-ids` (admin-only, mirrors the existing refresh route). Structurally tested against mocked Airtable/Graph data (this sandbox still can't reach the real services): exact matches, case-mismatch near-misses, and no-match cases all report correctly; dry run writes nothing; a confirmed run writes only the matched records. Delivered as `phase4-object-id-backfill.patch` plus a summary doc, same workflow as Phase 3 — built and verified against the actual current `dev` (not a stale copy), and applies cleanly. **Update, Sep 3: confirmed applied** to the current tree (`server/lib/elderObjectIdBackfill.js` exists on disk; the patch no longer applies cleanly, which is the expected signature of already-merged work).

**A detour worth recording: the `dev`/`main` drift from Section 9 turned out to be partly a false alarm on my end.** After Nathan applied and pushed the Phase 3 patch, my session's own git fetches kept reporting `origin/dev` as stuck on the pre-Phase-3 commit even after real troubleshooting on Nathan's side (checking GitHub Desktop, comparing branches, fetching). It turned out my sandbox's plain `git fetch origin dev main` was silently failing to update the local `origin/dev` tracking ref, for reasons tied to this environment's git proxy/refspec handling — a `git ls-remote` direct query and an explicit forced refspec fetch (`git fetch origin +refs/heads/dev:refs/remotes/origin/dev --force`) both showed the true state immediately: `dev` already matched `main`, byte-for-byte. So Nathan's original push (and the PR merge) worked correctly the whole time — the apparent ongoing drift after that point was a stale-read artifact in my own verification, not a real repository problem. Worth remembering if a future check here reports something that doesn't match what GitHub Desktop shows locally: cross-check with `git ls-remote` or a forced explicit-refspec fetch before treating my read as authoritative.
